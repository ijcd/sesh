# sesh v0.4 — plugin SPI + first non-terminal plugin (editor) — design spec

**Date**: 2026-05-25
**Status**: Design draft (pending review)
**Builds on**: v0.3 (global config, `include:`, `sesh init`, direnv connector). Pre-v1 — no backwards-compat constraints.

## Goal

Define the seam for non-terminal sidecars and ship one (emacs) as the proof. Terminal drivers (tmux, kitty) host children; plugins are leaves — a project may declare them, drivers don't contain them. Three things:

1. **`Plugin` interface** — narrower than `Driver`; no `Status`, no `Capture` (initially), no containment.
2. **Schema slot per plugin type** — top-level `editor:`, later `browser:`, `comms:`, etc. One key per type, validated at load.
3. **Emacs plugin** — `emacsclient` first; spawn daemon if absent. Workspace-per-project via `tab-bar` (built-in).

No new drivers. No changes to terminal containment. Plugins compose orthogonally with any driver.

## Strategic decisions

| Axis | Choice | Why |
|---|---|---|
| Plugin vs Driver | Separate interface, separate registry | Different responsibilities — drivers host, plugins don't. Sharing forces stub methods. |
| Schema shape | Per-type top-level keys (`editor:`, `browser:`) | Self-documenting; YAML-validatable; merge semantics obvious. Generic `plugins: [...]` deferred until 3+ types exist. |
| Lifecycle order | drivers.Up → plugins.Up; plugins.Down → drivers.Down | Plugins often need terminal layer first (browser→localhost). Reverse on teardown. |
| Identity | Project name = workspace key | Already the convention for tmux session / kitty tab prefix. Plugins inherit. |
| Idempotency | Plugin.Up MUST detect existing state and reuse | emacsclient over emacs --daemon; browser tab-group lookup before create. |
| Capture | Out of scope for v0.4 | Terminal capture is the load-bearing use case. Plugins add later via optional `Captureable`. |
| Plugin registry | Same shape as driver registry (`engine.RegisterPlugin`) | Familiar. Same lookup, same lifecycle, distinct namespace. |
| Per-plugin failure | Hard error by default; `optional: true` flag for opt-in soft-fail | Default surfaces config bugs early; opt-out for genuinely optional sidecars. |

## Plugin interface

```go
// internal/plugins/plugin.go
type Plugin interface {
    Name() string                                    // "emacs", "chrome", "slack"
    Up(ctx context.Context, p *spec.Project) error
    Down(ctx context.Context, name string) error
    Validate(p *spec.Project) []error
    DryRun(p *spec.Project) ([]string, error)        // shell-commands a real Up would run
}
```

No `Status` (most editors/browsers don't have a clean "is project X open" concept distinct from "is the app running"). No `Capture` (deferred). No `AttachCommand` (plugins don't take over the terminal).

Plugins read only the slice of `*spec.Project` relevant to them — emacs reads `p.Editor`, browser reads `p.Browser`, etc. A plugin whose slot is absent returns `nil` from `Up`/`Down` (no-op). Sets to `Up` are idempotent: re-running on an already-up workspace must not error.

## Schema additions

```yaml
# ~/.config/sesh/projects/liberties.yml
driver: kitty
cwd: ~/work/liberties
editor:
  plugin: emacs                # required; identifies which plugin handles this slot
  files:
    - ./README.md
    - ./mix.exs
  workspace: liberties         # optional; default = project name
  optional: false              # default false; true = soft-fail if plugin errors
tabs:
  - title: dev
    cmd: claude --continue
```

Validation:
- Unknown top-level plugin keys → error (`unknown plugin slot %q`).
- `editor.plugin` references unregistered plugin → error at validate (`no plugin registered for %q`).
- Each plugin defines its own sub-schema; unknown keys within a plugin's config → error.

Merge (with `include:`):
- `editor:` is a map; deep-merged per existing rules.
- Sub-fields override per type: `files:` is a list (append, parent first); scalars replace.
- `editor: null` in child drops the inherited plugin entirely (parallel to `drop: true` on tabs).

## Lifecycle

```
sesh up <name>
  ↓
config.Load → spec.Project (with .Editor populated)
  ↓
engine.Validate (drivers + plugins both validate their slice)
  ↓
hooks.pre
  ↓
driver.Up                         (terminal layer)
  ↓
for each registered plugin slot in spec.Project:
    if slot is populated:
        plugin.Up
        on error: hard-fail unless slot.Optional
  ↓
hooks.on_project_start

sesh down <name>
  ↓
for each registered plugin slot in reverse registration order:
    if slot is populated:
        plugin.Down (best-effort; log error, continue)
  ↓
driver.Down
  ↓
hooks.on_project_stop
```

Plugin ordering within a single Up: registration order (deterministic). v0.4 ships only emacs so ordering is unobservable; documented now to lock semantics.

## Emacs plugin

Three modes, auto-selected:

1. **emacsclient available + daemon running** — `emacsclient -e '(progn ...)'` evaluates a workspace-setup form.
2. **emacsclient available + no daemon** — `emacs --daemon=sesh` then mode 1.
3. **No emacsclient on PATH** — Validate-time error.

Workspace setup form (built from `editor.files`, `editor.workspace`):

```elisp
(progn
  (tab-bar-mode 1)
  (tab-bar-new-tab)
  (tab-bar-rename-tab "liberties")
  (find-file "/Users/ijcd/work/liberties/README.md")
  (find-file "/Users/ijcd/work/liberties/mix.exs"))
```

Down: `emacsclient -e '(when (tab-bar-mode-p) (tab-bar-close-tab-by-name "liberties"))'`. Idempotent; missing tab = no-op.

Daemon stays alive after `sesh down` (one daemon, many projects). User kills with `emacsclient -e '(kill-emacs)'` if desired.

### Why tab-bar, not perspective.el / persp-mode

Built-in (Emacs 27+), no external dep, well-understood. Future config option to use `perspective.el` for users who prefer it; not in v0.4.

### Function-level sketches

`internal/plugins/plugin.go`
- `type Plugin interface { ... }` — per signature above.
- `type Registry struct { plugins []Plugin }` — ordered slice, not map; preserves registration order for deterministic dispatch.
- `(r *Registry) Register(p Plugin)` — appends; refuses duplicates by Name.
- `(r *Registry) Get(name string) Plugin` — linear scan, fine at this scale.

`internal/plugins/emacs/emacs.go`
- `func New() *Plugin` — like kitty.New(): lazy binary lookup at first Up.
- `(d *Plugin) Up(ctx, p)` — builds elisp form, picks mode 1/2/3, dispatches via shared `dexec.Runner`.
- `(d *Plugin) Down(ctx, name)` — single `emacsclient -e` close-tab form.
- `(d *Plugin) Validate(p)` — checks `emacsclient` in PATH if `p.Editor != nil && p.Editor.Plugin == "emacs"`; checks all `files:` are non-absolute or live under `cwd`.

`internal/plugins/emacs/elisp.go`
- `BuildSetupForm(workspace string, files []string) string` — pure; returns a single elisp form. Files quote-escaped, paths absolutized against cwd before call.
- `BuildCloseForm(workspace string) string` — pure.

`internal/engine/up.go`
- `runPlugins(ctx, p, plugins)` — new helper; loops in registration order; respects `slot.Optional`.

## Errors added

| Class | Format |
|---|---|
| Unknown plugin slot | `~/.config/sesh/projects/%s.yml: unknown plugin slot %q (registered: editor)` |
| Plugin not registered | `editor.plugin: no plugin registered for %q (registered: emacs)` |
| Plugin Validate failure | `<plugin name>: %v` (per-plugin error wrapped at engine boundary) |
| Required plugin failure during Up | `plugin %s failed; rerun with editor.optional: true to soft-fail` |

## Out of scope (v0.5+)

- Browser plugin (Chrome / Firefox tab groups) — v0.5.
- `comms:` plugin (Slack channels, Discord) — v0.5/v0.6.
- macOS Spaces integration — v0.5 with browser plugin (both need NSWindow handles).
- `Captureable` interface for plugins — when capture demand emerges.
- Generic `plugins: [...]` list shape — when 3+ plugin types coexist and per-type keys feel cramped.
- `perspective.el` / `persp-mode` config option for emacs — opt-in extension after tab-bar baseline ships.
- Multi-plugin dependency graph (browser waits for server) — current answer: use `hooks.on_project_start`.
- Plugin-side capture/dogfooding — see "Out of scope".

## Unresolved questions

1. Plugin discovery — bake plugins into the binary (current plan) or load `.so` at runtime? Recommendation: bake; revisit at v1.
2. `editor.plugin` defaulting to `$SESH_EDITOR_PLUGIN` env, or always-explicit? Recommendation: always-explicit for now.
3. Per-plugin global defaults in `~/.config/sesh/config.yml`? E.g., `editor: { plugin: emacs }` as the implicit default if a project says `editor: { files: [...] }`. Defer until felt.
4. Emacs daemon name — hardcode `sesh`, or per-project? Recommendation: hardcode; one daemon serves all projects via separate tab-bar tabs.
5. Hook position for plugins — before or after `pre_window` is applied to terminal panes? Recommendation: plugins run after driver.Up returns, fully independent of `pre_window`.
